# Sigelith Hourglass — formats and algorithms (phase 0 draft)

Status: **DRAFT**, 2026-10-19. The `p0` identifiers belong to the phase 0 measurement and may
change; `v1` is defined only after phase 0. This is the public English version of the
operator's specification; the executable form is `reference/hourglass_ref.py` (Python,
standard library only). Test vectors: `vectors/vectors.json` (generated by
`reference/gen_vectors.py`). Tests: `python -I -m unittest discover -s tests -v`. The production
prover must produce the same bytes as the reference implementation.

**Hourglass is a proof of sequential work (PoSW) after Cohen and Pietrzak, not a VDF.** A VDF
from hash functions alone does not exist in the random-oracle model (Guan, Riazanov, Yuan,
CRYPTO 2025; Abusalah et al., EUROCRYPT 2026); the absence of a unique output and the
coefficient c (§6) are the price of any construction built from hashes only.

---

## 0. Glossary

| term | meaning |
| --- | --- |
| segment j | one hash tree computed from the seed χ_j; j = 1, 2, 3, … |
| n | depth of the segment tree; 2ⁿ leaves, N = 2ⁿ⁺¹ − 1 nodes |
| ℓ_v | label of node v (32-byte SHA-256) |
| φ_j | root of segment j (= the root's label); φ_0 — the genesis root |
| χ_j | seed of segment j |
| t, γ_i | number of checks and the checked leaves (Fiat–Shamir) |
| π_j | proof of segment j (file `<j>.proof`) |
| λ | security level in bits, with a margin for grinding (§6) |
| c | share of the steps guaranteed by the checks (`claim_permille`) |
| k, s_max | the explicit assumption about hardware advantage, and the highest measured prover speed (nodes/s) |

## 1. Constants, tags, identifiers

- Hash function: SHA-256 (FIPS 180-4). Labels and digests: 32 raw bytes; in JSON — 64 lowercase
  hex characters.
- Version tag: `p0` (phase 0) or `v1`. Prefix P: `sigelith-hourglass-p0` / `sigelith-hourglass-v1`.
- Domain separators (ASCII bytes): `P|node|`, `P|challenge|`, `P|seed|`, `P|genesis|`.
- Format identifiers: p0 — `sigelith-hourglass-p0-genesis`, `sigelith-hourglass-p0-segment`;
  v1 — `sigelith-hourglass-genesis-v1`, `sigelith-hourglass-segment-v1`.
- Ranges: 1 ≤ n ≤ 48, 1 ≤ t ≤ 1024, 1 ≤ λ ≤ 256.

## 2. Segment graph

- Node v = (d, b): depth d (0 … n) and the value b of its d bits (first bit most significant).
  Root = (0, 0). Children of (d, b): (d+1, 2b) and (d+1, 2b+1). Leaf u = (n, u).
- Edges: every child → its parent; and for every leaf u and every i = 1 … n where the i-th bit
  of u is 1: an edge from node (i, (u ≫ (n−i)) − 1) — the left sibling of the node on the path to
  u at depth i.
- **Parents:** of an internal node (d, b) — (d+1, 2b), (d+1, 2b+1) in this order; of a leaf u —
  the left siblings on its path, from the root down (increasing i).

## 3. Node label

```
enc(d, b) = 1 byte d ‖ BE64(b)                                  (9 bytes)
ℓ_v       = SHA-256( P|node| ‖ χ ‖ enc(v) ‖ ℓ_p1 ‖ … ‖ ℓ_pm ‖ 0^(32·(M − m)) ),   M = max(2, n)
```

- The input has **one fixed length for all nodes** of a segment: L = |P|node|| + 32 + 9 + 32·M
  (for p0 and n = 32: 1092 bytes, 18 SHA-256 blocks; the first block is the same for every node,
  so a prover computes 17). Every call therefore costs the same number of compressions, and the
  proven time follows from the average speed.
- Zeros pad the input **at the end**. A constant prefix could be computed once for many nodes.
- The number of parents follows from v (the verifier knows it), so the padding is unambiguous.
  The depth in enc(v) distinguishes leaves from internal nodes.

## 4. Order of computation (post-order with a stack)

```
stack ← []
for u = 0 … 2ⁿ − 1:
    ℓ ← label(leaf u, parents = labels on the stack, bottom to top)
    push (n, u, ℓ)
    while the two top entries have the same depth d:
        pop the right (d, ·, r) and the left (d, b, l); push (d − 1, b ≫ 1, label(node, [l, r]))
φ ← the single entry left on the stack (depth 0)
```

- Before each leaf the stack holds **exactly** its parents, from the root down. Every node depends
  on the previous one, so this is one sequential path through all N nodes. Memory: O(n) labels.
- **Answering checks without the whole tree:** the prover keeps the top levels 0 … n − m and, for
  a check, recomputes the subtree of 2^(m+1) − 1 nodes below the leaf's ancestor at depth n − m,
  starting from the labels of the left siblings on the path to that ancestor (`subtree()` in the
  reference implementation). Subtrees are independent; the prover computes them in a separate
  thread.

## 5. Checks, proof, verification

```
γ_i = first n bits of SHA-256( P|challenge| ‖ χ ‖ φ ‖ BE32(i) ),   i = 1 … t
```

- γ_i does not depend on t, so **the proof for t is a prefix of the proof for a larger t** — phase 0
  computes proofs with a large t and evaluates a smaller t from the prefix.
- **Proof π:** for i = 1 … t in turn: the labels of the siblings of the nodes on the path from leaf
  γ_i to the root, at depth n, n − 1, …, 1. In total t · n · 32 raw bytes, no header. The leaf
  label is not included — the verifier computes it from the leaf's parents (the left siblings
  contained in the proof).
- **Verification** of each check: (1) the leaf label from its parents; (2) up the path: parent =
  label(node, [left, right]), one child being the current label and the other the sibling from
  the proof; (3) the result equals φ. Cost: t · (n + 1) SHA-256 calls (p0, n = 32, t = 256: about
  50 ms in Python).

## 6. Guarantee, λ and c

- Cohen–Pietrzak: whoever made fewer than (1 − α) · N sequential calls passes t independent
  checks with probability at most (1 − α)ᵗ (plus a negligible term for 256-bit labels). The exact
  statement and constants for the Fiat–Shamir version are **to be confirmed against the papers**
  (Cohen, Pietrzak, EUROCRYPT 2018; quantum: Blocki, Lee, Zhou 2021; Chung, Fehr, Huang, Liao,
  EUROCRYPT 2021).
- **Grinding the root is cheap.** With Fiat–Shamir, a cheater who computed part of the tree can
  change a "junk" leaf at the end and get a new root — and new checks — for about n hashes per
  attempt, in parallel. The success chance grows linearly with the number of attempts q:
  ≈ q · (1 − α)ᵗ (demonstrated by the test `test_grinding_the_root_is_cheap`). Therefore
  **λ = λ_target + log₂ q_max**; by default 40 + 60 = **100** (a margin for 2⁶⁰ attempts within one
  segment).
- `claim_permille` = the largest p ∈ [0, 1000] with pᵗ · 2^λ ≤ 1000ᵗ — in integers. A record claims
  only c · N steps of its segment.

| t | λ | c (‰) | proof at n = 32 |
| --- | --- | --- | --- |
| 64 | 40 | 648 | 64 KB |
| 128 | 100 | 581 | 128 KB |
| 256 | 100 | **762** | 256 KB |
| 512 | 100 | 873 | 512 KB |

- **Phase 0 parameters:** t = 256, λ = 100 (c = 0.762); the t = 128 variant is evaluated from the
  proof prefix. The choice for v1 follows phase 0, together with the segment length (at t = 256 a
  proof of age for one year is about 2.2 GB with hourly segments and about 110 MB with daily
  ones).

## 7. Canonical JSON, genesis, inputs, seed

- Canonical JSON: the same subset of JCS (RFC 8785) as Sigelith checkpoints: ASCII keys, integers
  only with |x| < 2⁵³, strings without control characters, UTF-8, sorted keys, no spaces, no
  trailing newline.
- Time: `canonical_utc` — `YYYY-MM-DDTHH:MM:SS.ffffffZ` (always six fraction digits and `Z`), as
  in the log.

**Genesis** — exactly these fields:

| field | content |
| --- | --- |
| `v` | `sigelith-hourglass-p0-genesis` (v1: `sigelith-hourglass-genesis-v1`) |
| `hash` | `"sha-256"` |
| `n`, `t`, `lambda` | initial parameters (§1, §6) |
| `checkpoint` | `{"n", "sha256"}` — the latest `beattime-checkpoint-v1` (number and SHA-256 of the file) |
| `btc` | `{"height", "hash"}` — the newest known Bitcoin block |
| `utc` | `canonical_utc` of creation (server clock) |
| `k_assumed` | the assumed k (integer ≥ 1) |
| `s_self_nodes_per_s` | speed from the start-up benchmark |

```
φ_0 = SHA-256( P|genesis| ‖ JCS(genesis) )
x_j = SHA-256( JCS({"btc": {"hash", "height"}, "checkpoint": {"n", "sha256"}, "utc": <start of segment j>}) )
χ_j = SHA-256( P|seed| ‖ BE64(j) ‖ φ_{j−1} ‖ x_j )
```

- The genesis file is stamped in the log like any other file.
- The inputs are the newest data at the start of the segment (older data only weakens the
  segment's own "not earlier than"). The prover stores the inputs and the seed durably before it
  starts computing.

## 8. Segment record and proof file

Record (`segments/<j>.json`, j with at least 6 digits) — exactly these fields:

| field | content |
| --- | --- |
| `v` | `sigelith-hourglass-p0-segment` (v1: `sigelith-hourglass-segment-v1`) |
| `j`, `n`, `t`, `lambda` | segment number and its parameters (may differ between segments) |
| `prev_root` | φ_{j−1} (hex) |
| `inputs` | `{"btc", "checkpoint", "utc"}` from §7; `utc` = start of the segment |
| `seed`, `root` | χ_j and φ_j (hex) |
| `proof` | `{"file": "<j>.proof", "sha256": <SHA-256 of the file>}` |
| `utc_end` | end of the segment (`canonical_utc`) |
| `gaps` | list of interruptions `{"from_node", "utc_stop", "utc_resume", "reason"}` |
| `speed` | `{"nodes_per_s_min", "nodes_per_s_median", "nodes_per_s_max"}` — integers |
| `ptb_offset_us` | the latest offset of the server clock to PTB in µs, or `null` |
| `k_assumed` | the assumed k at the time of the segment |
| `claim_permille` | = the formula of §6 for the segment's t and λ |
| `coverage_permille` | ⌊1000 · N · 10⁶ / (`nodes_per_s_max` · µs from `inputs.utc` to `utc_end`)⌋ — information about the clock's operation, not part of the proof |

- File `<j>.proof`: the raw proof bytes of §5 (t · n · 32 bytes).
- Rules: `inputs.utc` ≥ `utc_end` of the previous segment (for j = 1: ≥ the genesis `utc`);
  `utc_end` > `inputs.utc`; `nodes_per_s_min` ≤ median ≤ max. There is no separate start field —
  the start is `inputs.utc` (it is in the seed).
- `gaps`: `from_node` = number of nodes computed before the interruption, in the order of §4; the
  prover resumes at leaf u, so `from_node` = 2u − popcount(u). `utc_stop` = the last durable state
  save before the interruption, `utc_resume` = the resumption. Reason in phase 0: `restart` (the
  process or the machine stopped — the prover cannot tell which). An interruption changes neither
  labels nor the root; it only lowers `coverage_permille`.
- `speed`: speeds of consecutive computing windows of at least 1 s (nodes in the window / window
  time); min, median and max of these windows. A segment shorter than one window: one value =
  N / segment time.
- `ptb_offset_us`: the "System time" field of `chronyc -c tracking` in µs, read by the sync in the
  last minute before `utc_end`; **positive = the server clock is behind PTB**, negative = ahead
  (the sign chrony uses in CSV mode). Only when chrony follows a PTB time server (its source
  address among the DNS addresses of `ptbtime1…4.ptb.de`); with another source, no DNS, or no
  answer from chrony — `null`.
- In phase 0 records are not signed; each one is stamped in the log like any entry. v1 adds a
  signature by the log key.

## 9. Checking the chain; forks

1. φ_0 from genesis; for j = 1, 2, …: `prev_root` = φ_{j−1}; χ_j recomputed from `prev_root` and
   `inputs` = `seed`; SHA-256 of the proof file = `proof.sha256`; the proof passes §5; the rules of
   §8; `claim_permille` and `coverage_permille` match their formulas.
2. Numbering continuous from 1, no holes.
3. **Fork:** two different `root` or `seed` values for the same j — within one source or between
   sources (our publication, archived copies) — are an incident, not an error to skip
   (`find_forks()`).
4. Consistency outside the proof: record times against the times of the records' stamps in the
   log, confirmed by the cosigners.

## 10. Elapsed time and minimum age (integers)

```
Δ_min(A, B) = ⌊ Σ_{s=i..j} claim_permille_s · N_s / (1000 · k · s_max) ⌋   seconds
```

- A was absorbed into the seed of segment i (directly or through a checkpoint —
  `absorbing_segment()`), B contains φ_j. Only complete segments i … j count.
- **Minimum age** of an entry: the same with j = the newest published segment (the record of
  segment j is the file B).
- s_max: the highest measured prover speed over the whole period (conservative). With several
  clocks — one common reference speed.
- A result always carries its assumptions: k, c (t, λ), s_max, n, the range of segments.

## 11. Test vectors (`vectors/vectors.json`)

- `chi` — a fixed test seed = SHA-256 of the string `sigelith-hourglass test vector`;
- `trees` — roots for n = 1, 2, 3, 4, 8, 12 (for n ≤ 3 also all labels as `[d, b, hex]`), node
  count and input length;
- `proofs` — checks, the proof and its SHA-256 for (n, t) = (4, 8) and (8, 16);
- `claim_permille` — a table [t, λ, p];
- `chain` — genesis and two segments (n = 4, t = 8, λ = 4 — TEST parameters) with proofs,
  `inputs_digest_1`, an interruption in segment 2 and an example of the Δ_min arithmetic.

The vectors are checked by a test that recomputes everything, including an independent recursive
method straight from the graph definition.

## 12. Open in this draft

- The exact theorem for the Fiat–Shamir version (§6) — to be confirmed with the papers before v1.
- k and s_max — from phase 0. Until then k is only "assumed".
- Parameters of v1 (n, t, λ, segment length) — after phase 0.
- The prover's state file is an implementation detail, not a public format (`state.txt`, format
  `sigelith-hourglass-state-1`: segment number, φ_{j−1}, seed and inputs of the current segment,
  next leaf, label stack, interruptions; next to it an append-only journal of the tree's top
  levels).
